## 协议与发布次序

当前仅支持固定 `openai-bridge` / schema 1；不在本轮扩大为通用服务框架。App 的完整契约文档规定：先发布兼容 App，再发布组件，用户明确配置或迁移后才注册。未来 schema 先由 App 同时支持新旧版本，再由组件写新注册；旧 App 对未知 schema 不执行脚本，但仍能清固定残留注册并按受管文件卸载，不因契约未知而永久卡住。

坏注册/坏安装元数据的降级不是“已停服”：不执行不可信目标、不猜进程、不递归删私有目录。只有合法实例的卸载入口失败才保留包供排错；普通卸载不 purge。组件更新也不覆盖既有私有管理器，迁移和回滚须另行确认。

## 从现用手工桥迁移：只做方案，不自动执行

现用手工桥不能与新组件默认管理入口混用。已有运行实例不会自动因组件更新而获得新安全修复或契约。

迁移前须单独确认维护窗口及可能中断的请求，再按顺序：

1. 用户保留自己的私有配置备份，不向AI、仓库或诊断材料提供其中内容；保留当前能用的接口与手工桥文件作为回退依据。
2. 先在不同端口、独立运行目录验证正式配套组件。由用户私下配置，测试时不抢现用端口、不覆盖现用Hook。
3. 完成正式八项验收后，再经确认停止现用手工桥/看护、撤掉它自己的精确Hook；不得按进程名批量停止或覆盖整份Claude设置。
4. 用户在App切到已验收的新端点；确认新建/恢复正常、没有重复看护及端口冲突。
5. 旧私有配置默认保留，不自动purge。只有另获永久删除授权才清真实数据。

任何一步失败，停止本次迁移：按身份只停新实例，移除新实例自身注册/Hook，保留其数据供排错；由用户切回原端点，并在得到许可后恢复原手工桥。若原服务仍健康，不为演练而无故重启。回滚也不得覆盖其他人的设置或删除会话。

不能说“已经修好，直接升级就行”。准确口径是：本地配套候选已通过列明的隔离门槛，正式配套发布与原生验收尚未完成。只有最终签名安装、真实更新和八项验收全部有证据，才标“已交付”。
