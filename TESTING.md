## New installed-App opaque-channel blocker — 2026-10-31

After the user reported another bridge interruption following an App-version update, the installed App code changed from the previously tested keyed base64url wrapper to **`http://127.0.0.1:<port>/u/<32-hex-HMAC-route>`**. Installed App tag: `3233e1c94728`; streamfix SHA-256: `a9dd527dbda3b20798ed831fbc68bdfd7683bdffbee2fc0cba47f3b57daf60f7`. The original URL exists only in the gateway's in-memory route map. The route is not an encoding of that URL and must not be treated as one.

- Read-only status at diagnosis: daily bridge `/health` returned `ok`; watchdog and CCR had started at **2026-10-31T01:55:53Z** (device-local 09:55:53). The lifecycle log records that start, but does not establish what stopped the previous processes or who initiated this recovery. A healthy listener now is not proof that the reported interruption did not happen, nor proof of upstream inference.
- Both the daily Hook and the candidate Hook were copied into disposable fixtures. The installed pure `fixedBaseUrl` function generated routes with a fake HMAC key and fake route map; only a marker-writing fake watchdog was used. Direct targets dispatch as positive controls, while a current-format route for the same bridge silently returns0 without dispatching in **both** scripts. A foreign route also remains a no-op. No live key, provider configuration or upstream request was involved.
- The earlier 15 Hook checks, archive validation and two gateway cold-start runs remain evidence for the **previous decodable format only**. They do not cover this new route-table protocol. The candidate is consequently **blocked from submission as a current-App cold-start fix**; the prior audit passes do not resolve this compatibility gap.
- Recognizing any 32-hex route as this bridge would start it for unrelated custom providers and violate the scoped Hook boundary. Guessing the original URL, reading credential-bearing provider files or enumerating live gateway routes is not an acceptable repair. The recommended durable integration is for the App to pass explicit, non-secret loopback-target metadata (or invoke an opt-in scoped readiness hook before dispatch), then have the bridge validate its exact authority/port. This requires a separate App-side integration decision; no installed App files or real settings were changed.
- Public submission is paused at the user's request. No live restart or patch was performed during diagnosis. Since the daily bridge is currently healthy, no recovery action was necessary; any later live change still requires confirmation.
